3. **冲突先按原版处理。**未被本 PRD 明确授权改动的原有规则，以当前实现为准。若某项新增规则确实无法与原有行为同时成立，先列出冲突位置、用户可见影响和最小兼容方案，更新《产品需求确认》与《开发规划》并完成产品确认，再修改该处；不得默默采用预览做法覆盖原版。

## 1. 问题与目标

现有点单确认生成一份全局采购需求，周菜单是另一套按日期安排的数据；采购勾选不能入库。当用户既提前排了某日菜单，又在当天点单时，两套数据可能重复采购或互不相通。菜单菜名的做法入口还不够直接，快照页没有计时。

本版目标是在现有应用上增加**按真实日期关联的排单与采购计算口径**，使未来菜品需求有一致视图。每个日期包含“待分配”与五个餐次。点单页负责快速下单，周菜单页负责提前安排；两者关联到同一日期排单。菜篮子按日期排单计算采购缺口、标明来源，并把实际购买量登记入冰箱。当日菜单单独承载今天的待分配、五餐安排与做菜入口。这是业务数据的新增关联，不是移除现有点单、周菜单或历史数据的指令。

本 PRD 已获授权作为 V2.1.0 的增量开发范围。它对《产品需求确认》原有“周菜单不影响采购”“只有已确认菜品可排餐”“点单确认整体替换采购清单”“已买仅记录进度”等口径作明确局部更新；未涉及的旧功能和规则继续有效。最小兼容方案同步写入《产品需求确认》《开发规划》，并以第 0 节的原版优先原则约束实现与验收。

## 2. 页面职责与导航

| 页面 | 主要任务 | 数据关系 |
| --- | --- | --- |
| 点单 | 选择今天要吃的菜和份数，不要求先选餐次 | 确认后写入今天的“待分配”，记录来源与时间 |
| 冰箱 | 查看和维护实际库存 | 菜篮子按可用库存计算缺口；入库在这里新增批次 |
| 菜篮子 | 查看今天及未来的采购缺口、来源、已买进度和实际购买量 | 由日期排单及库存派生，确认入库后重算 |
| 当日菜单 | 只展示今天已有菜品的餐次与做菜入口；日期行提示待分配数量 | 读取今天的排单，不另存一份副本 |
| 周菜单 | 按周浏览任意真实日期，提前安排、调整及复用菜谱 | 读写同一份日期排单；保留现有历史、复制和营养能力 |
| 菜谱 | 新建、导入、编辑、浏览菜谱 | 排单时复制菜谱快照；后续编辑不改已排菜 |

保留现有手机底栏的顺序与标签：**点单 → 冰箱 → 菜篮子 → 周菜单 → 菜谱**。点击原有“周菜单”入口仍先进入原有周菜单；在其页面内，以两个等权、醒目的大 Tab 访问独立的**当日菜单｜周菜单**视图，选中态通过背景、文字和 `aria-selected` 同时表达。当日菜单固定查看今天；周菜单保留已实现的单日查看、星期日期条及一周总览入口，并确保一周总览能清楚查看七天的餐次和菜品。每一天保留添加、调整、待分配和菜谱跳转入口；历史复制及原有营养能力仍应可达。切换 Tab 后保留周菜单上次所看的周与视图。两页读取同一份按日期关联的排单，不新增或重排底栏入口。预览默认展示整周只是便于评审该新增展示状态，不规定正式应用改动原有默认视图。交互预览的头部、图标或示例排版不得覆盖正式应用的现有实现；Android 原版界面为交付基准。

**视觉基准（2026-09-26 修订）：**所有新页面与面板沿用现有 Android 应用的暖白页面、浅灰绿顶栏、黄色主操作、系统无衬线字体及紧凑列表；不启用此前预览的深绿色主题。新功能只扩展必要的操作与状态，不整体替换现有点单、菜篮子、冰箱、周菜单和菜谱页的视觉语言。

**组件复用（2026-09-26 评审补充）：**点单沿用现有搜索、分类栏、带菜品缩略图的紧凑列表、加减份数与选菜栏；菜谱库沿用搜索筛选、缩略图与列表行。当天日期使用现有周菜单式的紧凑标题行。菜谱详情和周菜单餐次管理使用现有页面式弹窗的浅灰绿顶栏、关闭按钮和内容结构，并在原有菜谱详情中补充计时交互。采购数量编辑与待分配等短操作继续使用简短面板。

**待分配信息层级（2026-09-26 修订）：**不把完整“待分配菜品”卡片放在已排餐次前。日期标题右侧仅在有待分配菜时显示可点击的“待分配 N 道”；无待分配时显示当日已排菜数量。点击按钮打开底部面板，逐道查看菜名、份数、菜谱及“选餐次”；分配后更新数量，全部分完时关闭面板。当日菜单只展示已有菜品的餐次，空餐次不占页面位置；没有已排餐次时显示简洁空态。点单确认成功进入当日菜单时，日期旁的数量立即更新，成功提示指向该入口；这道菜已经计入采购，打开面板或分配餐次都不增加采购量。

设计参考：[Samsung Food 的 Queue 与数量提示](https://support.samsungfood.com/hc/en-us/articles/35369657798548-Getting-Started-with-Meal-Planner)将未安排菜从周计划分开；[AnyList 的 Queue](https://help.anylist.com/articles/meal-plan-queue/)允许先选菜和形成采购，再决定安排。食光的待分配菜已明确属于今天，因此采用日期行数量入口和底部面板，避免再增加一个同级 Tab；这是基于上述模式与本产品任务的设计推断，不是照搬其界面。

## 3. 单一排单与时间戳

- 每条已排菜至少保存：用餐日期、餐次（五餐之一或“待分配”）、菜谱快照、整菜份数、来源（点单／周菜单）、创建时间和最近修改时间。用餐日期是业务日期，创建时间是操作记录，两者不能混用。跨时区或夏令时变化不能移动已存用餐日期。
- 点单页只针对**今天**；用户确认时，把本次每道选菜分别写入今天的“待分配”，保留各次点单的独立记录，不整体替换已有周菜单。同菜再次点单也新增一条待分配记录，用户可只移除误点的这条。点单无菜时不自动清空今天已排内容。若要移除已排菜，在当日菜单或周菜单中明确操作。
- 周菜单从**整个菜谱库**选择菜品，支持过去和未来日期；历史和未来日期都可查看、复制及编辑。过去日期不继续产生待采购需求。
- 从“待分配”分配到某一餐，是移动同一条排单；采购总份数不变。同一日期、同一餐次、同一道菜合并时只增加该餐的整菜份数一次。不同餐次的同一道菜视为两次用餐，分别计量。点单与周菜单若最终指向同一条日期／餐次／菜品，须保留来源记录，但采购只计算最终排单份数一次。
- 菜谱修改或删除后，已排菜仍保留安排时的食材、步骤、图片和用时快照；重新选择该菜才取新版本。

## 4. 点单确认

1. 点单选择菜和份数，点击“确认选菜”。确认面板**只列本次所选菜品和份数**，可返回修改；不展示之前的排单，也不要求此时选择餐次。
2. 确认后，本次选菜各自进入今天的“待分配”。与已有菜重复时不在确认面板中做冲突选择，也不覆盖或替换原安排；它代表用户又点了一份完整菜，采购按最终排单份数增加。用户可在当日菜单删除本次待分配记录，或调整已分配菜的份数。来源记录应保留每次点单的时间与身份，界面展示时可按日期、餐次、菜谱快照合并。
3. 确认写入成功后，当日菜单和菜篮子同步刷新；写入失败仍保留点单草稿，不宣称成功，也不产生半条排单。

## 5. 菜篮子：日期来源、数量与入库

### 5.1 自动生成与展示

- 菜篮子基于**今天及未来所有已排日期**计算食材需求；“待分配”也计入，但在分配餐次后不能再次计数。采购视图默认显示今天起 7 天，可切换“今天／未来 7 天／全部排单”；切换只改变当前展示及对应日期范围的缺口计算，不删除排单或已买待入库记录。正式实现按用餐日期先后分配库存，避免切换范围时重复占用库存。主行按规范化食材名与单位合并，显示当前范围“还缺 N 单位”。
- 页面沿用现有“还需买／总项数”工具栏、“预览与导出”、食材分类切换、可勾选的紧凑食材行和底部操作位置。主行只显示名称、数量、分类和库存差额；点击行尾“还需买／拟购买／已买”数量可直接修改购买量，长按主行也可打开同一个编辑面板。日期来源与复核信息收进食材详情面板。日期范围在列表上方；有已买待入库食材时才显示底部入库按钮，零项时隐藏。数量与详情点击区域在 Android 上至少 48 dp，外观仍保持紧凑。
- 同一食材服务多个日期时只出现一条合并购买项。详情面板显示明确的月日、星期、餐次、菜名和份数；相同日期、餐次、菜谱 ID 与快照版本的来源合并为一条，原始点单时间戳仍保留在记录中。不同日期、餐次或快照版本不能仅凭菜名合并。
- 每批库存只抵扣一次。过期库存不抵扣；预计用餐前过期的库存不能算作该餐可用。已计划用于较早日期的库存不能再次完整抵扣较晚日期的需求。保存期仅是参考，实物状态仍由用户判断。
- 适量／数量未知时显示“用量待确认”，不得显示虚假的精确缺口。不同单位保留独立条目；本版不自动做 g/kg 等换算。采购导出／分享同步显示日期来源和实际待购量。

### 5.2 实际购买与确认入库

- 勾选表示“已买，待入库”，不是“已经在冰箱”。点击行尾数量、从详情面板选择“修改购买量”或长按食材行，均打开同一个编辑面板；行尾数量须是可聚焦按钮，并提供读屏标签。修改的是**实际买到的数量**，不会回写菜谱用量或排单份数；数量为正数，单位固定为该条目单位。用量未知的条目须先填实际购买量才可勾选入库。
- 顶部显示“已买待入库 N 项”。点击后逐项核对名称、实际数量和单位，再确认入库；默认入库日期为确认当天，分类及参考保存期按现有冰箱规则生成，之后可在冰箱编辑批次。
- 库存批次与已买状态必须一次原子保存。保存成功后才清除对应勾选和购买量草稿；重复点击不得产生重复批次；失败保留原状态，提示重试。离线重启、备份恢复及手动同步应保留尚未入库的勾选和实际购买量。
- 入库后重新计算缺口：买多时多余量留在冰箱；买少时该食材仍显示剩余缺口。排单、库存或来源变化导致已买量不再匹配时，应提示复核，不能静默沿用旧勾选。
- “已买待入库”独立于当前采购缺口保存及显示。即使用户删改排单、切换采购范围，已买食材仍可见；缺口变化时提示复核，允许继续入库或取消勾选。未勾选但已填写购买量时，列表同时显示缺口与本次拟购量；勾选后突出实际已买量。

## 6. 当日菜单与制作

- 当日菜单先展示日期总览与待分配数量入口，随后只展示当天已有菜品的餐次；未排菜的早餐、午餐、下午茶、晚餐或夜宵默认隐藏。可见餐次仍按五餐先后顺序排列。用户点“待分配 N 道”，在底部面板逐道选择餐次，亦可单独移除误点的待分配记录；分配到原本隐藏的餐次后，该餐次立即出现。当天没有已排菜时显示简洁空态，不留五个空餐次。新菜由点单页确认后进入今天的待分配，再在当日菜单分配；当日菜单不提供直接从菜谱库新增菜品的入口。周菜单提前安排到今天的菜也会同步显示。菜名可打开快照与做法；已排菜可调整餐次及整菜份数或移除，移除后提供短时撤销。
- 周菜单原有的单日视图保持可用；其一周总览完整呈现七天，每天显示日期与五餐行，空餐次保持现有“添加菜品”入口。点击餐次行沿用原有管理方式，并增量支持从整个菜谱库安排菜品，直接写入对应真实日期；已排菜可查看菜谱及调整份数或餐次。待分配菜在对应日期显示入口。周菜单与当日菜单读取同一份日期排单，不存在独立副本或手动同步按钮。
- 周菜单保留现有周范围切换、星期日期条、“一饭一饮 三餐四季”视觉标题、五餐行与餐次管理面板，以及营养周回顾和历史菜单入口。整周展示是对原有一周总览的增强，不替换原有单日浏览或改变其默认状态；预览直接展示七天只是为了评审此状态。
- 冰箱沿用现有搜索、期限筛选、分类切换、拍摄／相册／手动添加、紧凑库存行、查看可做菜品和清空操作；采购入库新增的库存批次直接进入同一列表，并遵守原有批次编辑与期限规则。
- 已排菜名直接打开**安排时保存的菜谱快照**，展示完整食材、制作步骤和预设用时。有效用时可打开临时计时器；倒计时数字本身可点击，编辑分钟和秒后按用户输入的时长开始计时。支持开始、暂停、继续、重置；重置回到本次编辑后的时长，不回到菜谱预设值。编辑中的输入须大于 0 秒，关闭详情即结束，不新增后台服务；再次进入菜谱重新使用预设用时。无有效用时则不显示计时。
- 菜谱内容只读；临时修改倒计时时长不回写菜谱或排单快照。菜谱库内编辑、删除不改已经排好的快照。返回详情后保持当日菜单位置。查看做法和运行计时不自动减少冰箱库存。

## 7. 数据兼容与边界

- 升级必须保留原有菜谱、图片、库存、采购勾选、已确认快照、真实日期周菜单和历史菜单。新日期关联须兼容并继续读取原有周菜单数据；若确需迁移，先备份、验证完整性并保留回滚路径，不得直接覆盖或删除旧数据。若旧点单确认没有用餐日期或餐次，**不得猜成今天**，保留为“旧版待安排采购”，由用户选择日期／餐次后归入新排单或主动清除。
- 新排单来源、时间戳与待入库实际数量需纳入现有 SQLite 结构化状态、备份校验、手动同步及冲突比较。旧版备份兼容读取；同步冲突不能静默覆盖。
- 原有营养预计值、周回顾、历史复制与提醒须继续按日期快照工作。新增顶部 Tab 不得遮蔽这些能力。
- 本次不自动扣减烹饪时消耗的库存，也不记录个人实际摄入。若后续加入“做完扣库存”，要单独确定实际消耗量与库存批次选择规则。

## 8. 验收条件

**先决验收：**在验证以下新增流程前，先对照开发前基线检查原有点单、菜谱管理、菜篮子、冰箱、周菜单、营养、历史、提醒、设置、备份与同步的入口、布局和主要操作。原功能回归失败时，本版不能验收；不能以预览运行正常或新流程通过替代原功能回归。数据迁移还须用旧版真实数据验证保留与升级。

1. 不经点单确认，也能从周菜单中把菜谱库菜品安排到未来日期；菜篮子出现带日期、餐次和菜名的缺口。
2. 点单确认只核对本次选菜和份数；重复点单仍生成独立的待分配记录，用户可只删掉本次记录，原有安排和其采购量不受影响。
3. 点单成功后，当日菜单日期行立即显示“待分配 N 道”，未排菜的餐次仍隐藏；点开底部面板可逐道分配。分配到某餐后数量减少，该餐次出现或更新，菜篮子采购总量不变。周菜单同日期同步显示。待分配为零时不留空卡片或空白区。
4. 同食材来自多个日期时采购量合并、来源可逐条查看；库存不重复抵扣，过期及预计用餐前过期的库存不被误计。
5. 实际购买量大于缺口时入库保留多余库存；小于缺口时显示剩余待购；失败或双击不重复入库。
6. 点击当天菜名可直接看安排时快照、食材、步骤和计时；点击倒计时数字可修改时长，计时及重置均使用修改后的值；原菜谱修改／删除后快照仍可读。
7. 旧版数据升级、离线重启、备份恢复、手动同步及 Android 真机触控／键盘／系统返回均通过针对性验证；交付 APK 前完成既定签名及保留数据覆盖升级验收。
8. 手机周菜单入口保留原有名称、单日浏览和一周总览；页面内清楚显示“当日菜单｜周菜单”两个同级 Tab。从任一视图一击切换；进入一周总览时完整显示七天，切换周后仍保留用户选择的总览状态。从某天安排、查看菜谱或调整菜品后返回原有视图，切到当日菜单再回来仍保持所看周与视图。窄屏和放大字体下 Tab 与逐日操作仍可辨认与点按。
9. 菜篮子行尾数量可点击及键盘聚焦，进入与长按相同的购买量编辑面板；保存后行尾从“还需买”变为“拟购买”并显示用户输入量，原缺口仍在详情中可查。勾选后显示实际“已买”量，入库按该量计算。

## 9. 本轮评审要确认的口径

- 点单先进入“待分配”、随后在当日菜单分配餐次，已按用户本轮反馈定为草案口径。
- 菜篮子默认展示今天起 7 天，可切换今天或全部排单；已买待入库记录始终独立可见，库存分配须按日期避免跨范围重复计量。
- “制作完成”是否要在后续版本显式扣减库存；本版仅有菜谱与计时，不自动扣库存。

## 10. 评审发现与预览修订

- **采购来源重复展示（2026-09-26）：**同一天、同一餐次、同一菜谱快照重复点单时，主界面合并为一条来源并累计份数、用量；原始点单时间仍留在数据中。预览已演示合并显示，正式实现还需使用快照版本参与分组，并完成迁移和持久化验证。
- **独立 UI 审阅与后续反馈（2026-09-26）：**预览把点单确认简化为仅显示本次所选，并将周菜单改为七天总览；后续统一回现有应用的视觉主题，菜篮子主行也恢复紧凑展示，来源与修改量转入详情面板。它仍是内存演示，库存批次保质期、SQLite 原子入库、历史数据迁移、系统返回及 Android 触控需在正式开发时验证。
- **现有页面交互保留（2026-09-26）：**菜篮子、冰箱与周菜单继续使用当前应用的主要布局及操作入口；新增的日期排单、采购来源、入库闭环叠加在现有结构中。周菜单原有单日视图、日期条和五餐管理保持原样，一周总览展示七天；预览中的设备拍摄、历史复制与营养统计只显示入口和说明，正式开发需对接原有功能。
- **视觉统一复审（2026-09-26）：**点单与菜谱库预览改用现有应用的列表结构，当日菜单日期信息收为紧凑标题行；菜谱和周菜单餐次管理改用页面式弹窗。菜篮子零项入库按钮隐藏，并扩大行尾数量与详情的可点区域；正式 Android 实现仍须真机核对触控尺寸。
