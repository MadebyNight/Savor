## 目标与实施约束

交付紧凑、统一的 Android 个人膳食应用，修正识别入口，支持五餐安排、库存期限辅助和营养周报。沿用 React + Vite + Capacitor、SQLite、私有图片目录和 Keystore，不更换框架。首页米白、暖黄、灰绿视觉延伸至全部二级页面。

保留采购按确认份数计算、菜单独立快照、历史复制、离线保存与同步冲突保护。不覆盖现有未跟踪的 `tests/android-native.mjs` 和 `接入文档指引图片/`。不自动提交、发布或安装到用户设备。

## 已确认口径与拟定细节

- [x] 营养统计：用户确认先统计“菜单预计营养”，明确不等于个人实际摄入。本版不增加实际食用份量登记，不引入人数分摊。整菜营养乘以餐次安排份数后按周汇总；同一道菜安排多次，营养分别计入各餐，采购规则保持不变。
- [x] 提醒渠道：用户确认必须同时支持应用内提醒和关闭应用后的 Android 系统通知。
- [x] 提醒设置：用户确认应用内提醒时间可自定义；不能仅在固定的周末时刻弹出。
- [x] 统一时间：默认周日 20:00，可修改星期和本地时间；应用内与系统通知共用一套时间，分别开关，不提供两套独立时间。通知点击进入对应周，不自动请求 AI。
- [x] 回顾周期：默认周日回顾本周一至周日的菜单预计营养，包含已安排的周日晚餐和夜宵，给出下周建议；标题为“本周菜单营养回顾”，明确显示起止日期。自定义提醒仍针对该次计划提醒所属周；跨周补看保留原目标周，不按打开时间错误切换。
- [x] 去重：前台到时仅应用内提醒，不额外发送系统通知；后台或关闭时按系统通知开关发送。再次进入应用，若未查看该周回顾且应用内提醒开启，保留一条非弹窗提示。查看该周营养回顾即可停止两端该周提醒并清理对应通知，无需生成 AI 报告。
- [x] 营养路线：可靠食材数据优先本地计算，不足时由用户主动触发 AI 补充估算并确认发送；标明来源，保存结果供离线查看，缺失值不当作零。
- [x] 临期阈值：总保存期 ≤3 天时剩余 1 天、4–7 天时剩余 2 天、超过 7 天时剩余 3 天开始提醒。阈值仅控制提醒，不证明食物安全。
- [x] 未知与覆盖：无法可靠估算时标注“保存期待补充”，允许入库和后续补填，不归入正常状态、不编造期限。包装标示期限或用户手动值优先于自动估算；修改保存方式提示重新估算，不静默覆盖手动值。
- 保存期只能是指定保存条件下的参考期限，不证明食物安全；包装标示及实际状态优先。规则数值须有可靠来源后才能落地。
- 本次不引入个人健康目标、疾病诊断或自动饮食处方；周报给出一般膳食结构建议，不把计划当成实际摄入。

## 开发顺序与阶段门槛

1. 界面方向已确认，以界面设计规格和实施计划进入分批开发准备；不自动安装或发布。
2. 开发获准后完成 P0：记录现状、同步冲突文档，再进入 P1。每阶段先完成相关测试再标记完成。
3. P1 识别流程完成后实施 P2 全局布局，避免先美化即将被替换的识别界面；P2 的共用规范供 P3–P5 沿用。
4. P3 五餐模型先于 P5 营养统计，P4 期限计算与现有采购抵扣一起验证。
5. P5 按“离线营养汇总 → AI 周报 → 提醒设置 → Android 通知”实施；每一步可独立验证，但不能以应用内提醒代替系统通知交付。
6. P6 全量回归、Android 构建与真机验收后，再核对版本、交付产物和 Git 提交范围。每次进度更新列明已完成、未验证和阻塞事项，不预先勾选。

#### P5.1 数据口径与离线估算

用户已确认“本地计算＋AI 补充估算”：优先可靠食材数据，不足时提供主动发起的 AI 估算，发送前确认，按来源保存供离线查看。具体数据源、匹配算法和字段仍需技术核验，不再将整体路线列为待用户选择。

- [ ] 核验营养数据来源、许可、可离线使用范围及常见中国食材覆盖率，记录生熟状态、可食部和数值单位。来源选型是实现前门槛，不用无出处数值填表；不能覆盖的食材明确待补充。
- [ ] 第一版按食材可食重量和每 100g 营养参考值计算整菜估算，不把烹饪水分变化等同营养增加；未知用油、调料、弃汤等标注估算限制。
- [ ] 明确单位换算：g/kg 可换算；ml 仅在有对应密度时换算；个、把、勺等需用户确认克重或可靠换算依据。未知数量和“适量”不得默认为零。
- [ ] 为缺失项提供 AI 补充入口，明确发送范围；区分本地参考值和 AI 假设，保存估算来源、时间及输入快照。AI 返回按缺失食材/指标合并，不能将整菜估算再叠加到本地合计造成重复计算；无法可靠拆分时保留缺失，不静默覆盖可靠本地值。
- [ ] 验证未授权无请求、离线/无 Key 提示、失败保留已有结果、取消忽略迟到响应、输入变化使旧估算失效、AI 非法数值拒绝写入、混合来源无重复及离线/备份恢复可读。
- [ ] 营养字段拟定为 `energyKcal`、`proteinG`、`fatG`、`carbohydrateG`、`fiberG`；未知值用 null 表示，零只用于明确为零的数值。各指标分别计算覆盖情况，部分结果标为“已知部分合计”。
- [ ] 食材参考信息拟包含 `foodId`、`grams`、`source`、`sourceVersion`、`basis`（生/熟及可食部说明）；菜谱保存 `nutrition` 估算快照，包括指标、缺失项、计算版本和时间。
- [ ] 安排菜单时复制营养快照；旧菜单不写回当前菜谱的新估算，若缺少历史营养则显示未估算。用户可明确发起历史重新估算，并标记重新估算时间。
- [ ] 按五餐的菜单快照与 servings 汇总；显示本周预计营养、每日分布、数据覆盖与待补充食材，不显示“你已摄入”。覆盖率按各指标可计算的食材条目数/总条目数表示，不能冒充重量覆盖率。
- [ ] 单测覆盖重复安排、份数、五餐、缺失单个指标、未知单位、零值、空周、快照稳定性；E2E 覆盖编辑食材后新安排更新、旧安排保持原快照。

#### P5.2 AI 周报

- [ ] 周报入口展示目标周日期、预计营养汇总、数据缺失提示，以及实际将发送的食材类别汇总；确认后才发送给已配置服务商。
- [ ] 提供一般膳食结构分析和下周调整建议；数据不足时说明不足，不对个人实际摄入或健康状况下结论。仅有宏量营养不能可靠推断蔬果/全谷物情况，需使用明确分类汇总或说明无法判断。

#### P5.3 应用内提醒与设置

用户已确认统一时间、分别开关、按前后台分流，以及查看营养回顾后停止该周提醒。以下字段为实现命名提案，行为以已确认规则为准。

- [ ] 在设置增加“营养周报提醒”：应用内与系统通知两个开关、共用每周几和时间，默认周日 20:00。保存后展示下一次提醒时间，非法时间不能保存。
- [ ] 本机偏好拟包含 `inAppEnabled`、`systemEnabled`、`reminderWeekday`（ISO 1–7）、`reminderTime`（HH:mm）；通知权限状态从系统读取，不伪造为设置值。
- [ ] 提醒标识采用目标周起始日期；记录 `lastInAppPromptedWeek`、`lastSystemNotifiedWeek`、`lastReviewedWeek`。前台仅按应用内开关提醒，后台/关闭仅按系统开关通知；不开启的渠道不被另一渠道自动替代。查看该周营养回顾即标记已查看，两端不再重复提醒，不以生成 AI 报告作为条件。
- [ ] 返回前台时未查看者显示一条非弹窗提示，遵循应用内开关；一次仅保留最近到期周，不补发历次弹窗。跨周打开定位原目标周；正在编辑时不覆盖输入。
- [ ] 修改时间取消旧调度并计算下一次；关闭某渠道只影响该渠道，不清除营养或周报。周数据为空时明确“该周没有安排”，不自动请求 AI。
- [ ] 单测覆盖周界/跨年、时间修改、时区变化、重复打开、已查看、空周与无效偏好；浏览器验证设置持久化、前后台切换和提醒点击定位目标周。
- [ ] 增加周日完整计划（含尚未到时的夜宵）、自定义星期仍汇总计划周、跨周补看、仅查看汇总即去重，以及前后台切换与通知触发竞态测试；不重复发通知或清除尚未查看的目标周提示。

## 验收口径与风险

“一屏”指常规手机默认字号下的基本表单或含 10 道菜的五餐内容，不承诺无限数量菜品和完整长菜谱强行一屏。紧凑布局保留可操作区域。食品保存和营养明确估算限制，不输出虚假的精确摄入或安全保证。首次进入页面与恢复草稿必须稳定，且离线核心功能不能被 AI 配置阻断。
