# 食光 · 开发规划

v0.1 · 2026-09-14｜实现基线：原型 `a393227`

本文用于确定这个小应用的开发方向、功能范围和实施顺序。“已有”指当前代码，“计划”指后续开发；业务规则的暂定值仍可调整。现状详见[产品需求确认稿](产品需求确认.md)，视觉与交互基准见[设计逻辑](设计逻辑.md)。

## 1. 目标与范围

围绕“选菜 → 安排三餐 → 生成采购清单 → 管理冰箱”的日常流程，保留现有五个模块和美术交互，补齐实际使用需要的功能，接入云端 AI 和个人跨设备同步。

已确定采用 GitHub Pages 托管前端、DeepSeek 提供 AI、坚果云保存同步数据，并增加轻量云函数处理网盘中转。优先使用免费额度和平台自带网址，暂不购买服务器或域名。AI 按实际调用计费，网盘与云函数超出免费额度时再评估费用。

首版暂按个人在手机、电脑之间使用规划；百度网盘作为后续替换或扩展方向。家庭成员管理、多人实时协作、自动营养核算和 AI 自动排餐尚未确认为需求，暂不排入本轮开发。

## 2. 技术方向

| 部分 | 方案与职责 |
| --- | --- |
| 页面 | 沿用 React + Vite，在 GitHub Pages 发布静态构建；保留米白暖黄配色、菜品卡片、侧栏/手机抽屉、弹层、拖放与操作反馈。 |
| 本地数据 | 使用 IndexedDB 保存菜谱、图片、库存、选菜、菜单、历史和偏好；同站点升级时迁移当前 `localStorage` 数据，切换网址时通过完整备份导入、导出迁移。 |
| AI | 默认 DeepSeek，支持 Chat Completions 和 Responses；可配置接口地址、模型、协议与 API Key，分别适配请求和流式输出。暂不接入 Anthropic 协议。 |
| 云端数据 | 使用坚果云 WebDAV，同步结构化业务数据和独立图片文件；网盘承担持久保存，本地仍可独立操作。 |
| 云函数 | 负责网盘读写中转，以及支持范围内的公开网页正文获取；选择有免费额度、默认 HTTPS 地址且访问可用的平台，具体平台在接入阶段确定。 |

个人 AI Key 在各设备上填写，优先由浏览器直连 DeepSeek；以后需要共用 Key 时再改由云函数调用。坚果云的浏览器跨域限制由中转解决。无需另外建设业务数据库。

DeepSeek 当前支持两种协议及图片输入，可用于菜谱和小票识别；Responses 的兼容范围不包含会话持久化及内置网页搜索，应用自行保存所需数据。链接导入需要先取得正文；需要登录或无法读取的网页，提示改为粘贴文字、上传截图或手动录入。

## 3. 功能实现范围

| 模块 | 已有实现 | 计划补齐 |
| --- | --- | --- |
| 点单选菜 | 分类、菜名搜索、菜谱详情、食材与步骤、用时与热量、份数增减、点单清单和确认操作。 | 统一选菜份数、餐次份数与采购用量；明确选菜是待安排内容、周菜单是实际安排，调整容易混淆的“同步”文案。 |
| 菜谱管理 | 手动录入菜名、分类、用时、成品重量、热量、食材和步骤；增删食材/步骤、拖动步骤排序并保存。 | 编辑、删除已有菜谱，上传图片；接入文字、图片和链接导入；修改或删除菜谱不破坏历史菜单记录。 |
| 菜篮子 | 按确认份数汇总食材、抵扣库存、分类筛选、清单预览、PNG 和 Word 导出、浏览器分享。 | 按确定的采购规则重新计算；菜单或库存变化后更新缺口；完善空清单提示和分享不可用时的导出/复制入口。Word 首版沿用现有 `.doc` 导出。 |
| 周菜单 | 拖放或点击安排七天三餐、重复安排、移除菜品、餐次/每日热量、目标提醒、保存和清空、查看存档。 | 按实际日期切换周、设置餐次份数、持久保存热量目标；历史菜单可复制到指定周；按目标周保存，避免只用保存当天日期导致覆盖。 |
| 我的冰箱 | 增删食材、修改数量和单位、保存期限提示、按所选食材找菜。 | 拍照和小票识别后编辑、确认入库；支持修正录入日期和保存期，保留手动维护库存；找菜时明确提示仍缺少的食材。 |
| AI 录入 | 只有入口和未接入提示。 | 提取菜谱字段或食材清单，先展示可编辑草稿，确认后保存；数量、单位、热量缺失时提示补充，估算值作标记；处理等待、取消、失败重试和手动录入。 |
| 保存与同步 | 当前浏览器 `localStorage` 保存业务数据，无跨设备同步。 | IndexedDB、旧数据迁移、备份恢复、坚果云连接设置、自动/手动同步、最近同步时间、失败提示和冲突处理。 |

新增设置、AI 草稿和同步状态沿用现有界面风格；电脑保留拖放，手机保留点击操作，避免功能只能通过拖拽完成。

## 4. 首版业务规则

以下为规划默认值，其中采购口径、份数与人数、菜谱维护范围和日期复用仍需确认。

- **采购依据：** 建议以选定周菜单的实际总份数计算。选菜清单用于准备待排菜品，不再另外叠加采购量。例如一道菜在三餐各安排一份，应按三份汇总，再抵扣库存；未安排时提示先完成排餐。
- **份数和热量：** 暂定一份是菜谱中的整道菜，食材和热量随餐次份数换算；默认展示整餐/整天总热量，并保存每日目标。是否增加用餐人数和个人摄入换算，开发前确认。
- **食材与库存：** 首版按同名、同单位合并抵扣；单位不同提示修正，不自动推断重量与体积的换算。查看清单或安排菜单不扣库存，实际购入、消耗先由用户手动调整。按库存找菜时保留“同时包含全部所选食材”的规则，另提示菜谱其余食材的缺口。
- **日期与历史：** 菜单按真实周和餐次保存；复制历史菜单后可独立修改，清空当前周不删除其他周。保存菜单时保留必要的菜谱快照，避免后续菜谱维护改变历史记录。
- **AI 结果：** 识别结果先成为草稿，不直接覆盖菜谱或库存；用户可以修正并确认。不从菜品照片直接推断准确重量、保存期限或营养值。
- **跨设备同步：** 网页打开或恢复联网时比较本地与云端版本后同步，本地修改后合并短时间内的同步请求再上传，并提供手动同步。离线改动保留，网页关闭后不承诺持续后台同步。上传前检查云端版本，结合条件写入或版本副本避免覆盖；两端都有修改时保留副本并提示选择，不静默覆盖。保留最近若干个备份版本，具体数量在接入时确定。

## 5. 开发顺序与完成标准

| 阶段 | 主要工作 | 完成标准 |
| --- | --- | --- |
| 1. 基础功能与数据 | 确认第 4 节规则；统一份数、采购和日期；补齐菜谱维护、图片、历史复用、库存提示；迁移 IndexedDB 并支持备份。 | 不使用 AI 也能完成“录入菜谱 → 选菜排餐 → 查看采购缺口 → 维护库存 → 保存复用”；刷新后数据保留，原有数据可迁移和恢复。 |
| 2. AI 接入 | 增加配置，接入两种协议；完成图文菜谱、公开链接、拍照和小票导入，补齐识别草稿与失败处理。 | 两种协议均可完成适用的录入流程；识别内容可修改，确认后落入对应模块；失败时仍可手动完成录入。 |
| 3. 坚果云同步 | 接入 WebDAV 云函数中转、图片与业务数据同步；处理离线、版本冲突、备份和状态提示。 | 手机、电脑能读取同一份数据；切换设备后能获取更新；失败和冲突有明确提示，能够从副本或备份恢复。 |
| 4. GitHub Pages 上线 | 按 GitHub Free 条件使用公开发布仓库；适配 Vite 仓库子路径及资源地址，配置 GitHub Actions 构建发布，整理首次配置和跨网址数据迁移说明。 | 在正式 Pages 地址下能打开各页面、加载图片，并完成 AI 录入和双设备同步；手机、电脑主要操作可用。 |

每阶段交付一个可审查、可使用的增量。先完成稳定的本地流程，再接入 AI 和同步，最后在正式站点地址上完成交付确认。

## 6. 安全与验证边界

按个人小应用处理：API Key、网盘应用密码和中转访问凭证不写入仓库、发布文件或普通同步包。网盘中转保留基本访问验证，限制网盘目标与操作目录；输入做必要的格式和数量检查。

不建设复杂账号权限体系、审计平台或企业级安全设施，不安排专项渗透测试或大规模安全测试。开发阶段以生产构建和关键流程人工确认作为交付检查，重点检查采购计算、AI 确认录入、备份恢复及同步冲突；不扩展成完整自动化测试工程。

技术依据：[DeepSeek Responses](https://api-docs.deepseek.com/zh-cn/guides/responses_api)、[图片输入](https://api-docs.deepseek.com/zh-cn/guides/vision)、[坚果云 WebDAV](https://help.jianguoyun.com/?p=2064)、[GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/about-github-pages)。服务能力和免费额度以实际接入时的官方说明为准。
