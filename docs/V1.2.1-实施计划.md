# V1.2.1 实施计划

2026-09-21。状态：界面方向已确认，开发准备完成到任务拆分；正式应用尚未修改。

## 目标、架构与技术栈

目标见 [TODO](V1.2.1-TODO.md)，界面验收以[界面设计规格](V1.2.1-界面设计.md)及其链接的最后确认预览为准。沿用 React + Vite + Capacitor、SQLite 结构化状态、私有图片目录、Preferences 与 Keystore。优先提取现有代码，避免重做存储、同步、网络或引入新 UI 依赖。

## 工作顺序与改动控制

- 已确认的识别与 UI 工作可先进入实现。P4 保存规则、P5 营养来源和提醒默认策略仍需分别收口，不因界面获认可就视为已确认。
- 每批先查看 Git 与相关文件；不覆盖 `tests/android-native.mjs`、`接入文档指引图片/` 等已有未跟踪内容。
- 保留预览文件用于验收，不直接复制独立 HTML 的演示数据、事件脚本或多层 CSS 覆盖。
- 不自动提交、安装手机、发布或推送。删除文件及测试产物按工作区规则二次确认。

## 第一批：基线与文档对齐

目标文件：`AGENTS.md`、`docs/产品需求确认.md`、`docs/开发规划.md`、`README.md`、`docs/V1.2.1-TODO.md`。

1. 在正式开发前把旧“排除营养”改为菜单预计营养；不引入个人实际摄入。同步五餐、识别独立入口、库存参考期限、双渠道提醒。
2. 标明当前已实现功能与 V1.2.1 待实现功能；README 不提前写成新功能可用。
3. 启动本地预览并保存现有页面截图及脱敏测试日志，作为改动前对照。运行现有 Node 测试：`node --test src/domain.test.js src/validation.test.js src/ai-connection.test.js src/sync.test.js`，用 PowerShell `Tee-Object` 保留输出到 `.android-tools/v1.2.1/`，明确退出状态。

完成条件：文档边界无冲突，已知基线失败单独记录。现状截图不是新版验收。

## 第二批：业务识别页从设置中分离

目标文件：`src/App.jsx`、`src/components/SettingsPanel.jsx`、拟新增 `src/components/RecognitionPanel.jsx`、`src/storage.js`、`src/components/DraftEditor.jsx`、`tests/e2e_ai.py`、`tests/e2e_ai_review.py`、`tests/e2e_back.py`。

1. 把识别输入、读取配置、请求、核对结果的现有流程提取到 RecognitionPanel；设置仍负责凭据与服务配置，不复制请求实现。
2. 定义三种明确的界面模式：菜谱图文、菜谱正文、冰箱拍照；从 App 传入入口和返回目标，设置返回原任务。
3. 图片入口支持相册/拍摄；正文只展示正文与公开链接；冰箱点击直接触发 capture 图片输入。取消相机不请求 AI、不清空旧草稿。
4. 草稿按任务隔离；旧 `ai-draft` 根据 kind 迁移，菜谱旧草稿若同时有文字和图片需完整保留，不因新界面隐藏某字段而丢弃。迁移完成标记和失败恢复需在代码实现前补充精确方案。
5. 保持发送前确认、重复请求防护、失败保留、取消忽略迟到响应及批量保存的原有规则。

验收用例：三个入口到对应页面；设置返回不二次选模式；关闭和重启草稿仍在；拒绝发送无请求；只保存选中条目；接口错误不把草稿写入正式数据。相机由浏览器 mock 检查入口、由设备验证实际唤起。

## 第三批：共用样式、紧凑列表与短表单

目标文件：`src/styles.css`、`src/styles/mobile.css`、`src/App.jsx`、`src/components/Dialog.jsx`、`src/components/DraftEditor.jsx`、`src/components/SettingsPanel.jsx`、`src/components/SyncPanel.jsx`、`tests/e2e_mobile.py`、`tests/e2e_settings.py`、`tests/e2e_ai_review.py`。

1. 建立少量共用表单/分区样式，使用已确认颜色与层级；在现有规则处收敛，而非持续添加高优先级覆盖。
2. 系统字体及继承覆盖输入、选择、按钮和弹窗；核查原生字号缩放，再决定是否修改 `android/app/src/main/java/com/shiguang/mealplanner/MainActivity.java`，不先硬编码 textZoom。
3. 先接入库存手动表单与识别核对，共用名称/分类/数量单位/期限行；库存行打开底部编辑面板，识别核对按需展开条目字段，保留部分保存行为。
4. 将同一规范应用到确认点单、导出、菜谱编辑、设置等页面。全屏长任务与底部短任务按规格分工。
5. 做截图对照及长名称、默认/大字体、软键盘压缩、空数据和失败状态检查；局部警示加强不等于变更期限算法。

验收用例：输入框有可见边界与焦点；长文字不截掉关键信息；360×800 默认字号的库存基本字段和提交可见；320px 宽无横向溢出；错误不只靠颜色，键盘弹出后提交仍可达。生产样式预览也要验证，避免仅开发模式通过。

## 第四批：五餐与直接显示营养区

目标文件：`src/domain.js`、`src/domain.test.js`、`src/components/MobileWeek.jsx`、`src/App.jsx`、`src/validation.js`、`tests/e2e_mobile.py`。

1. 集中定义餐次：保留旧 key `早/中/晚`，新增下午茶与夜宵的明确 key，检索其他硬编码消费者后统一引用。
2. 单日表直接显示十道基准菜名与份数，点餐次进入底部管理；七天总览复用同表结构，slogan 为“一饭一饮 三餐四季”。
3. 验证下午茶与夜宵安排、重启、备份往返、历史复制与旧三餐兼容；菜单变动不改变采购。
4. 营养模块未完成前仅实现布局及“未估算/—”状态，不使用预览假数字。P5 算法就绪后接入选中日期汇总及部分估算提示，默认展开。

验收用例：2/3/1/3/1 道菜在常规视口五餐可见；完整菜名在长内容时可滚动；日期切换数据正确；历史快照不受菜谱删除影响；营养不以个人摄入名义展示。

## 完成与交付

所有行为变更更新有价值的测试；测试先保存日志。浏览器回归按当前脚本实际 URL 启动服务器，执行相关 `python tests/e2e_mobile.py`、`python tests/e2e_ai.py`、`python tests/e2e_ai_review.py`、`python tests/e2e_back.py` 等，失败先定位，不随意削弱断言。

最终按 `npm run build` → `npx cap sync android` → Android 构建验证；工具路径和 JDK/SDK 环境沿用 `scripts/android-build.ps1`。实际接入通知和字体后补真机验收，先运行日志脚本。覆盖升级和真实服务未验证时明确标记。`git diff --check` 后更新完成清单、询问是否提交，仅提交相关文件。
