# 食光用户体验与功能评估

评估日期：2026-09-22

评估对象：当前工作区源码、手机已安装的 V1.2.1（versionCode 4）

性质：评审记录与优化建议，不是已批准的需求变更或全量验收报告。

## 1. 结论

当前主要问题是：功能已经分开实现，但日常使用仍需用户自己串联选菜、排餐、采购和库存维护。部分高频任务需要跨页面往返，部分页面优先展示说明、装饰和管理按钮，实际操作内容靠后。

现有米白、绿色和暖黄色的视觉方向适合家庭饮食场景，可以保留。优化重点应是任务衔接、状态解释、信息排序和空间分配，而不是整体换肤。

优先顺序：先保护草稿与计算可信度，再打通采购和库存操作，随后调整主要页面，最后补齐后台提醒、外部服务及大数据量验收。

## 4. 功能合理性与完整性

### F-01 未确认选菜与已确认采购的状态解释不足

**依据：真机观察、代码确认。** 本轮手机上点单显示“已选 0 份菜品”，菜篮子同时显示“还需要买 14 种食材”。两份状态独立符合当前规则，但用户容易理解为同步错误。

建议明确区分“本次待确认”与“当前采购计划”，展示采购来源，并提供修改当前计划的入口。不要用合并状态的方式破坏已确认采购。

### F-02 操作文案暗示了未实际发生的结果

**依据：代码确认。** “确认我的菜单”“加入菜单”“确认后同步到周菜单”容易让人以为完成日期和餐次安排。实际确认只更新采购需求及可安排菜品。

建议统一为“确认选菜”“加入待选”，成功后提供“去安排餐次”。同时区分采购份数和餐次份数。

### F-03 采购清单缺少购物过程

**依据：真机观察、代码确认。** 当前更接近缺口计算结果，缺少已买勾选、实际采购数量、快捷入库；临时添加采购项也不方便。

优先补已买和入库，再决定是否支持独立的手动采购项。无需直接扩展成复杂购物管理系统。

### F-04 库存维护成本会影响采购可信度

**依据：代码确认、产品建议。** 如果每次做饭都必须自己计算剩余量并修改表单，长期使用容易忘记维护。库存失真会继续影响采购缺口。

建议提供主动确认的消耗操作。不应仅因菜单已安排就自动扣库存，计划不等于实际做过。

### F-05 “看看能做什么”与实际筛选算法不完全一致

**依据：代码确认。** 实现要求菜谱同时包含所有选中食材，且是名称严格匹配。选择鸡蛋和牛奶会排除只含其中一种的菜；匹配成功也不意味着其他食材齐全。候选食材直接遍历全部库存，包含已标记过期的批次。

建议区分“包含所选食材”与“库存基本能做”，过滤过期批次，展示还缺什么；多选采用全部匹配还是任一匹配，应在界面说明。

### F-06 保存方式修改与重算期限耦合

**依据：代码确认。** StockFields 中保存方式改变直接调用重算。已有期限时，取消重算也取消保存方式改变，同意则替换期限。用户不能方便地改保存方式并保留包装期限。

建议拆分为修改保存方式、保留原期限、主动重算三个明确行为。参见 [StockFields.jsx](../src/components/StockFields.jsx)。

### F-07 包装到期日录入不够直接

**依据：代码确认、产品建议。** 表单以入库日期和保存天数为主。包装印有到期日期时，用户需要自己换算，并理解入库日算第 1 天。

建议允许直接填写到期日期，保存天数保留为另一种输入方式，避免两个字段相互矛盾。

### F-08 营养补缺操作成本偏高

**依据：代码确认、产品建议。** 本地参考数据覆盖有限，补充偏逐菜、逐项操作；重复安排保留独立快照，对相同输入可能重复完善。

建议先展示本周缺失项汇总，再考虑相同输入复用结果。更新已有历史快照仍需明确选择，不自动写回所有历史菜单。

### F-09 后台提醒可靠性尚未完成验收

**依据：历史记录。** 开发进度记录这台 OPPO 的后台调度曾被延迟约三天。诊断触发的通知展示、点击成功不能替代定时投递验收。

本轮没有重做长时间后台测试。后续需验证前后台、划掉任务、进程回收、重启及时间变化，实际行为和界面承诺保持一致。参见 [开发进度](开发进度.md)。

## 5. 前端实现问题与风险

### FE-01 高优先级：切换编辑对象会覆盖现有菜谱草稿

- **证据：代码确认。** 菜谱详情的编辑按钮直接执行 `setRecipeDraft(structuredClone(activeRecipe))`，前面没有检测未保存草稿或确认放弃。
- **触发场景：** 编辑菜谱 A 未保存，离开后打开菜谱 B 并点击编辑。
- **影响：** A 的未保存草稿被替换；草稿本身还会随状态持久化，不能把“离开保留草稿”理解为始终安全。
- **建议：** 发现不同对象的未保存草稿时，让用户继续原草稿或明确放弃后编辑新对象。
- **限制：** 未使用手机真实草稿做破坏性复现。
- **位置：** [App.jsx](../src/App.jsx)，详情编辑动作，评估时约第 1547 行。

### FE-02 高优先级：采购没有 g/kg 等价换算

- **证据：独立复现、代码确认。** 输入需求为番茄 500g，库存为番茄 1kg，期限未知；实际仍输出需采购番茄 500g。
- **原因：** 单位做了文字规范化，但采购按规范化后的单位完全相等抵扣，没有统一基准单位。
- **影响：** 用户按包装录入 kg、菜谱使用 g 时可能重复购买。
- **建议：** 先支持确定的同量纲换算，如 g/kg；“个、把、勺”等不做无依据换算。
- **定位：** [domain.js](../src/domain.js) 的 `normalizeUnit`、`procurement`。
- **性质：** 当前实现限制，现有测试也接受不同单位不抵扣；改动前需更新规则和测试口径。

### FE-03 中优先级：部分成功提示早于持久化完成

- **证据：代码确认。** 菜谱保存、点单确认先更新 React 状态并显示成功，实际保存由 effect 异步完成。
- **影响：** 本地保存失败时，可能先提示成功，再提示失败。
- **建议：** 关键提交动作在写入完成后提示成功；自动草稿保存与正式保存的状态区别表达。
- **位置：** [App.jsx](../src/App.jsx) 的 `saveRecipe`、`confirmSelection` 和自动保存 effect。
- **限制：** 本轮未制造存储失败。

### FE-04 中优先级：单张图片故障可能阻断整个数据加载

- **证据：待验证风险。** `loadState` 等待整个状态递归解码，图片读取错误会向上传播；没有单图片占位降级。
- **影响：** 一张图片文件丢失或损坏时，可能连菜谱文字和库存都无法进入。
- **建议：** 局部图片失败显示占位和提示，保留其他结构化数据可用。
- **位置：** [storage.js](../src/storage.js) 的 `decodeImages`、`loadState`。
- **限制：** 未进行图片损坏故障注入，不能记为已真机复现。

### FE-05 中优先级：全量保存及图片内存占用存在规模风险

- **证据：待验证风险。** 草稿输入会触发完整状态复制、排队保存；加载时读取图片为完整数据，缓存保留图片内容。
- **影响：** 大量菜谱和图片下可能出现输入延迟、内存增长、保存排队。
- **建议：** 先测实际数据规模，再考虑草稿保存合并、减少重复复制、按需加载图片，避免直接做大规模重构。
- **位置：** [App.jsx](../src/App.jsx) 自动保存 effect、[storage.js](../src/storage.js) 的 `saveState`、图片缓存。
- **限制：** 本轮没有性能压力测试，不宣称当前已经发生明显卡顿。

## 6. 页面视觉与风格评估

| 页面 | 观察与问题 | 优化方向 |
| --- | --- | --- |
| 点单 | 窄屏保留左分类栏，右侧还需容纳图片、菜名、食材和数量按钮；首屏菜品数量有限 | 先减少重复信息和非必要留白，再比较横排分类与现状的实际操作效率 |
| 冰箱 | 搜索、标语、拍照、分类、期限筛选逐层叠加，第一条库存约到半屏才出现 | 合并工具区，优先显示库存和临期摘要 |
| 冰箱状态 | 长状态标签在窄屏断行，占用较多横向空间 | 主标签缩短为已过期、今天到期、剩 2 天；详细解释放详情，保留必要警示 |
| 菜篮子 | 每项重复需要采购并使用警示色，但整页本来都是待采购项 | 以勾选状态、名称、数量建立层级，分类作为次要信息 |
| 菜谱详情 | 大图、时长、编辑和删除排在食材与步骤之前 | 优先支持看配方和做菜；图片收紧，管理动作进入次级菜单 |
| 新建菜谱 | 首屏先放上传及文件选择，分类同时提供输入框和建议按钮，保存位于长表单末尾 | 菜名和食材前置，图片可选；区别导入菜谱与添加图片，提供稳定保存入口 |
| 周菜单 | 营养回顾入口醒目，历史入口较弱；排餐、复用和查看做法的权重不足 | 强化日期、餐次、复制和做法入口，营养作为辅助层 |
| 设置 | 横向分页隐藏提醒，首先展示接口、模型及实际请求地址 | 设置首页采用功能列表，服务商提供预设，自定义技术配置收进高级选项 |
| 营养回顾 | 实现先展示 AI 建议，再展示已有每日营养 | 优先显示离线可用数据、缺失情况，再提供 AI 建议入口 |

### 6.1 复杂任务的承载方式

菜谱详情、餐次管理、营养回顾、高级计算都可能需要长时间浏览或编辑。多层弹窗虽然能工作，但上下文和滚动负担较大。建议复杂任务评估独立页面，简短选择继续使用弹窗，不要求统一替换所有弹窗。

### 6.2 保留和改进的边界

- 保留现有饮食场景配色、系统字体支持及底部主导航。
- 不通过压小字号或点击区域来追求一屏容纳更多内容。
- 不把所有说明删除；将低频说明移到详情，让核心状态与操作更靠前。
- 本轮没有完成颜色对比度或 TalkBack 全面检查，不给出无障碍全面达标结论。

## 7. 建议实施顺序

以下为排序建议，尚未授权执行修复。

| 批次 | 内容 | 验收重点 |
| --- | --- | --- |
| 1：数据与计算可信度 | 草稿保护、g/kg 换算、保存反馈、图片故障隔离 | 切换编辑不丢草稿；等价单位正确抵扣；失败不提示已保存；单图片失败不阻断业务 |
| 2：高频流程 | 餐次直接选菜、查看菜单做法、采购勾选入库、库存快捷消耗 | 核心任务减少跨页面往返；保持采购与排餐独立；保留快照和离线能力 |
| 3：页面层级 | 冰箱首屏、详情、新建表单、设置导航、术语统一 | 当前窄屏和系统字体下核心内容靠前；软键盘、返回、长文本不退化 |
| 4：可靠性 | 后台提醒、真实 AI 补缺和周报、坚果云往返、图片及菜谱规模测试 | 分别提供真实链路证据；不以模拟服务或诊断触发冒充完整验收 |

涉及业务规则变化时，再同步产品需求与开发规划。本报告本身不改变既定规则，也不将优化建议自动列为已确认开发任务。
