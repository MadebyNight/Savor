# 食光 · 产品需求确认稿

v0.2 · 2026-09-14 · 需求确认中｜实现基线：原型 `a393227`

本文用于确认功能和使用规则是否符合预期。“当前能力”描述已有实现，末尾区分已确认方向和待确认规则。开发范围、技术路线及阶段安排见[开发规划](开发规划.md)。

## 1. 产品目标与使用流程

按现有设计理解，食光面向日常为自己或家人做饭的人，帮助用户决定吃什么、安排一周三餐、弄清需要买什么，减少食材浪费。

主要流程：**选菜并确定份数 → 确认清单 → 查看采购缺口、安排一周三餐 → 保存安排。** 也可以先登记冰箱食材，再找包含这些食材的菜谱。

## 2. 功能范围

| 模块 | 当前用户能做什么 | 需要明确的规则与边界 |
| --- | --- | --- |
| 点单选菜 | 按分类或菜名找菜；查看食材、步骤、用时和热量；增减份数并确认清单。 | “点单”指制定自己的菜单。加减份数后，需要再次确认，才会更新采购需求和待排菜品。 |
| 上传菜谱 | 手动填写菜名、分类、用时、成品重量、热量、食材和步骤；增删食材及步骤、调整步骤顺序，保存到菜品库。 | 当前是新建菜谱，未提供已保存菜谱的编辑、删除；图片、链接识别尚未接入。 |
| 菜篮子（采购清单） | 汇总已确认菜品所需食材，抵扣冰箱已有数量；按分类查看，导出图片或 Word，分享清单。 | 同名且同单位的食材才能合并抵扣；采购量按确认份数计算，改变周菜单不会重新计算采购量。 |
| 周菜单 | 将菜品拖放或点选到周一至周日的三餐；重复安排、移除菜品；查看餐次和每日热量，设置目标提醒，保存或清空安排。 | 每次安排计一份，不受确认份数限制。当前是周模板，存档按保存日期记录，同日保存会覆盖；历史安排只能查看。 |
| 我的冰箱 | 添加、删除食材，修改数量和单位，查看保存期限提示；选中食材后查找菜谱。 | 采购或做完饭后需手动调整库存。找菜要求同时包含全部所选食材，不代表食材数量足够；新鲜度按录入日期和设定天数估算。 |

**采购规则示例：** 一道菜确认 1 份后，安排进 3 餐，当前采购清单仍按 1 份计算，可能少算实际需求。这是本次需要优先确认的规则。

## 3. 体验与能力边界

- **视觉与文案：** 延续米白底色、暖黄重点、菜品卡片、电脑侧栏和手机抽屉，保持“好好吃饭，好好生活”的轻松语气。关键操作应让用户明确当前是在选菜、确认采购需求，还是安排餐次。
- **智能能力：** AI 图文、链接、拍照和小票识别目前只有入口与提示，实际依靠手动录入；不支持从食材自动核算营养，也不会自动生成周菜单。已确定后续接入云端 AI 识别，具体范围见开发规划，尚未实现。
- **份数与热量：** 一份对应菜谱设定的成品重量；热量按整份菜计算，未按用餐人数分摊，不代表某个人的实际摄入。每日目标默认 2000 kcal，可修改，刷新后恢复默认。
- **数据保存：** 已保存的菜谱、库存、点单、周菜单和存档在当前浏览器中保留；刷新页面后，未保存的录入内容会丢失。当前没有账号、跨设备同步或多人共用数据的能力。

## 4. 已确认方向与待确认需求

第 1、6 项已确认技术方向，第 2–5 项仍需确认业务规则；开发规划已列出建议默认值。

1. **首版范围（已确认）：** 以现有五个模块为基础补齐功能，并接入云端 AI 识别；默认使用 DeepSeek，支持 Chat Completions 和 Responses，暂不考虑 Anthropic 协议。
2. **采购依据：** 按已确认选菜份数，还是按最终周菜单的总份数采购？建议以最终周菜单为准，避免重复排餐后漏算。
3. **份数含义：** 是否接受“一份就是菜谱中的整道菜”，还是需要用餐人数，以及食材用量和个人热量的换算？
4. **菜谱维护：** 首版是否需要编辑、删除已保存的菜谱？建议补齐，方便修正录入内容。
5. **日期与复用：** 是否需要按实际日期选择某一周，并将历史菜单再次用于排餐，还是现有周模板和存档查看已足够？
6. **跨设备同步（方向已确认）：** GitHub Pages 托管前端，坚果云 WebDAV 保存同步数据，轻量云函数中转。规划先按个人在多设备之间使用；家庭多人实时协作尚未确认为需求。以最小预算为目标，保留必要的安全措施，不做复杂安全设计和专项安全测试。

当前原型可作为讨论依据；以上确认结果再转化为具体改动，不默认把现有实现当作最终需求。
